# Field brief: continuous improvement loops for long-lived LLM agent systems

**Date:** 2026-08-18 · **Prepared for:** pressure-testing and implementing `research/improvement-loops.md` — a daily/weekly loop that evaluates a trading day's agent run and routes evidence into charter, memory, and config tuning, with human-gated authority · **Depth:** normal-to-deep, 7 searches, 11 sources read

## State of the field *(prose)*

Two communities are working this problem and barely cite each other. The **practitioner/vendor side** (Hamel Husain and Shreya Shankar's evals course and FAQ; observability vendors like Braintrust, Arthur, LangWatch) has converged hard on one loop: production traces → sampled scoring or classification → flagged traces to a human review queue → promoted into a permanent regression dataset → run in CI on every future change. That loop is stable enough that its shape is no longer argued about; what is argued about is how much of it a model may run unsupervised. The **academic side** has spent the last year quantifying why the naive version of this loop produces false confidence, and the numbers are worse than the folklore suggested — a 2025 study across 18 models and 2,361 hypotheses found incorrect conclusions in ~31% of hypotheses even for frontier models. What changed recently is that the failure modes stopped being theoretical: prompt-variant selection ("LLM hacking") and reflective-memory confabulation both now have measured instances with published rates, not just cautionary anecdotes.

The gap between the two sides is where the interesting work is. Industry tooling gives you *version control* for prompts — immutable registries, semantic versioning, environment pinning, pointer-swap rollback — but nothing that records the variants you tried and rejected. Academia recommends pre-registration and multiple-comparisons correction, but addresses that recommendation to researchers publishing papers, not to operators running a system daily. Nobody found in this pass runs a pre-registered, family-counted trial registry for prompts in production. That is a genuine hole, not an oversight to catch up on.

## Core concepts and vocabulary

- **Error analysis** — the systematic pass over production traces: open coding (free-text notes on what went wrong), axial coding (grouping into a failure taxonomy), iterate to theoretical saturation. The field's consensus starting point, and explicitly *not* the same thing as building dashboards.
- **Theoretical saturation** — the stopping rule for error analysis: keep reviewing until ~20 consecutive traces reveal no new failure mode.
- **Trace classification** — automated per-facet labels (task, sentiment, issue type) written onto each production trace by a scheduled job; the input to alerting and to regression-set promotion.
- **Regression promotion** — turning a flagged production failure into a permanent CI test case. The mechanism that makes the loop ratchet instead of oscillate.
- **Eval-driven development** — writing evaluators before the feature. Named mostly to be rejected: the failure surface is unbounded, so you write evaluators for errors you *observed*, not errors you imagined.
- **LLM-as-judge alignment** — validating an automated judge against human labels on a held-out labeled set, reported as TPR and TNR rather than raw agreement.
- **Matched-pair (paired) design** — scoring both variants on identical inputs and analyzing the per-example delta vector, so between-example variance cancels. The recommended comparison design.
- **MDE (minimum detectable effect)** — the smallest delta worth shipping, fixed *before* looking at data; drives sample size.
- **Shadow evaluation** — both variants score live inputs while only the incumbent serves. The check that your offline eval set still resembles production.
- **Canary / eval-gated rollback** — serve the challenger to 1–5% of traffic with cohort-stable hashing, monitor a rolling per-rubric pass rate, auto-revert on a threshold breach.
- **LLM hacking** — exploiting prompt-design flexibility until the result supports a desired conclusion; the LLM-native form of p-hacking, and the term the literature now uses.
- **Garden of forking paths** — the multiple-comparisons framing applied to undocumented prompt exploration: the problem is the undisclosed search, not any single choice.
- **Self-reinforcing error / memory confabulation** — a reflective agent writes a confident, causally wrong lesson, then acts on it forever, never gathering the evidence that would overturn it.
- **Reflection grounding** — requiring each written reflection to cite specific episodic evidence, producing an auditable trail. Partial mitigation only.
- **Summarization drift** — the retrieval-side failure: repeated compression passes silently drop low-frequency, high-importance detail.
- **Staleness management** — temporal versioning (newest wins), source attribution (user statement outranks agent inference), contradiction detection, scheduled consolidation sweeps that retire stale entries.

## Live debates and open questions *(prose)*

**How much of the review loop may an agent run?** This is the sharpest live disagreement and it maps directly onto the "have an agent do it" instinct. Husain and Shankar draw a hard line: do not automate initial open coding of raw traces, taxonomy validation, ground-truth labeling, or root-cause analysis; *do* automate first-pass categorization after a human has coded a batch, mapping annotations onto known failure modes, and pattern analysis over already-labeled data. Their stated reason is that reading raw traces is how you build product intuition, and automating it means you never acquire the thing the automation is supposed to scale — plus a blunt warning to be skeptical of tools promising to optimize prompts for you, especially early. They also want a single named "benevolent dictator," a domain expert, owning taxonomy decisions rather than a committee. Vendor tooling (Braintrust, and the observability field generally) implicitly disagrees by shipping daily automated classification over every trace with 1–10% scorer sampling and Slack alerting; their position is that the human enters at triage, not at coding. Both are defensible and they resolve differently at different volumes — the practitioner line is aimed at teams whose trace volume a human *could* read.

**Do offline evals earn their keep, or do they mostly manufacture confidence?** The 2026 arXiv paper *When Generic Prompt Improvements Hurt* argues that generic prompt improvements can raise eval-set scores while lowering production performance, because eval sets are too small to carry production diversity, and that iterative refinement — human or automated — induces overfitting as the optimizer exploits idiosyncratic artifacts. The vendor answer is procedural rather than a rebuttal: held-out sets, shadow evaluation against live inputs, and pulling production traffic into the eval set whenever the shadow delta falls outside the offline confidence interval. Nobody claims offline evals are sufficient; the disagreement is whether they are a screen (defensible) or a gate (contested).

**Reflect, or retrieve?** The 2026 memory survey (arXiv 2603.07670) and the *Honest Lying* confabulation study (arXiv 2605.29463) land on the same conclusion from opposite directions: reflection is high-yield and high-risk. Reflexion's headline result (91% pass@1 on HumanEval vs 80% baseline) is relayed everywhere, but the confabulation re-analysis of Reflexion's own logs found 32% of environments developed frozen memory in which *zero* of 121 stored reflections named the correct target. The proposed fixes split: the survey favors reflection grounding (cite your evidence) plus staleness machinery; the confabulation authors tested grounding and found it lost to **programmatic feedback extraction** — parsing the trajectory for failure signals rather than asking the agent to diagnose itself. Their diagnosis of *why* is the transferable part: binary pass/fail feedback with no step-level detail creates an information vacuum that the model fills with plausible, causally wrong stories.

## Practitioner heuristics *(prose)*

The people who do this well start from traces, not from metrics. The move that separates them is open coding: read a hundred real traces, write free-text notes, then group the notes into a taxonomy, and only then build a scorer for the failure modes that actually showed up. Teams that skip to dashboards and LLM judges are the recognizable anti-pattern, and prefab metrics — ROUGE, BERTScore, "helpfulness" — get eye-rolled specifically because they let you feel measured without learning anything; their one legitimate use is as a net for finding interesting traces to read. When they do compare two prompts, they compare them on identical inputs and look at the per-example delta rather than two independent means, they fix the minimum effect worth shipping before looking at the data, and they treat any result on fewer than ~100 paired examples as noise. They keep the prompt in a registry rather than in application code, version the whole execution context (model, params, tools, retrieval config — not just text), pin environments to explicit tags because "latest" reintroduces exactly the drift the registry exists to kill, and treat rollback as a pointer swap so reverting costs seconds and needs no deploy. On memory, the current default is retrieval over raw records as the substrate with reflection layered on top and constrained — every lesson cites its evidence, contradictions get flagged, stale entries get retired by a scheduled sweep — and the sharpest available finding is that when you can extract failure signals programmatically from the trajectory, you should, because a model asked to diagnose its own binary failure will produce a confident story instead.

## Coverage edges *(prose)*

Nothing here is domain-specific to trading or to outcome-labelled financial decisions, where resolutions arrive on a horizon rather than at annotation time — that difference matters for anything that scores a decision, and it was not searched. The auto-revert and sample-size numbers rest on a single vendor post with no academic or independent practitioner corroboration found, so treat them as a starting point to price against rather than as established practice. Reflexion, Generative Agents, LoCoMo and MemoryArena were read only through the 2603.07670 survey, so figures attributed to them are relayed rather than verified — and for the same reason the self-reinforcing-error claim was demoted to single-source at the landing gate: the survey states it, but a survey relaying others' work is not an independent second origin, leaving the *Honest Lying* re-analysis carrying that claim alone. Finally, the strongest negative finding is itself an inference from absence: no production system was found that pre-registers prompt trials and counts the family of variants attempted, which means a design doing so is unvalidated by prior art in either direction.
